cypera-core ​

cypera-core — pure domain for cypera, the org's reusable documentation/reference-generation tool.

Everything here is string/AST-shape in, markdown out — no I/O. cypera-cli owns filesystem walks, process spawning, and stdout; this crate owns the models and the renderers:

  • [manifest] — Cargo.toml decoding (workspace members + per-crate manifests).
  • [crate_map] — the crate-map model + markdown renderer (successor to the per-repo docs/gen-crate-map.py scripts).
  • [config] — Rust config-struct doc-comment scanning + the config-reference page renderer (successor to docs/gen-config-docs.py).
  • [cli] — the CLI-reference page wrapper for gen-cli-docs output (the clap-markdown markdown sibling CLIs emit).

Modules: api, cli, config, crate_map, error, manifest, repo_config. Entry: src/lib.rs.

cypera-driver ​

tamias-driver-cypera — the pavo driver for a cypera workspace, plus the engine ops surface.

Verbs (the tamias driver contract):

  • manifest — print the [DriverManifest] JSON (discovery probe; never touches workspace state).
  • capabilities — {"capabilities": ["pavo"], "verbs": […]}.
  • ops — the engine ops manifest: every bounded cypera CLI verb as a cli.<verb> wire query, derived from the engine's own clap tree ([cypera::command]). Unbounded/host-interactive verbs are surfaces, never ops (cypera has none today).
  • run <argv> — engine passthrough: tamias-driver-cypera run check ≡ cypera check. Also the child side of cli.* wire queries (ops::run_verb re-execs this same verb so engine output never touches the serve stream).
  • cli <cypera argv> — the tamias bins[] shim verb: tamias bin exec calls it with the standard --dir/--name driver flags ahead of the user's argv; they're stripped and the rest runs through cypera::run_from in-process with inherited stdio — full engine parity (--help/version, globals, --json, stdin-bound flags all work).
  • serve — ndjson JSON-RPC on stdio: {"op":"manifest"}, {"op":"views"}, {"op":"view","view":…,"params":{…}}, {"op":"query","query":…,"params":{…}} → {"ok":true,"result":…} / {"ok":false,"error":…}. query:"ops" answers the ops manifest; query:"cli.<verb>" runs the engine op.

Optional surface: feature mcp embeds pavo-driver-kit's surface layer — mcp serves the ops manifest as MCP tools on stdio, equivalent to the standalone tamias-driver-mcp surface driver minus the PATH/discovery hop. (cli needs no feature: it's the bins-shim passthrough above, not a generated surface — the engine's own argv grammar is the contract.)

Which repo: ops inherit the serve process's cwd — each verb's --repo/--config params map straight onto the engine's own flags, and absent them cypera's upward cypera.toml discovery applies, identical to running the cypera verb by hand. This driver ships no views — it is the engine-ops surface for cypera workspaces; view/query names outside ops/cli.* answer ok:false.

Modules: ops, surface. Entry: src/main.rs.

cypera-xtask ​

cypera-xtask — workspace automation: check / test / coverage / pack / install / fmt.

text
cargo xtask check      # fmt --check + clippy -D warnings
cargo xtask test       # cargo nextest run (falls back to cargo test)
cargo xtask coverage   # llvm-cov report (extra args pass through)
cargo xtask pack       # stage libraries/cypera driver payload
# (release tamias-driver-cypera → drivers/bin/<triple>/)
cargo xtask install    # release-build tamias-driver-cypera → ~/.local/bin
cargo xtask fmt        # cargo fmt --all

No module declarations. Entry: src/main.rs.

cypera ​

cypera — reusable documentation/reference generation for the 9aia org. The shared successor to the per-repo docs/gen-*.py scripts: one tool renders the crate map, CLI reference, and config reference pages every sibling docs site needs, driven by a per-repo cypera.toml discovered upward from --repo.

text
cypera gen crate-map [--repo <path>] [--config <path>] [--out <file>] [--layer <crate=layer>]…
cypera gen cli       [--repo <path>] [--config <path>] [--input <file|->] [--out <file>]
cypera gen config    [--repo <path>] [--config <path>] [--file <rs>]… [--out <file>]
cypera gen api       [--repo <path>] [--config <path>] [--out <dir>] [--target-dir <dir>]
cypera check         [--repo <path>] [--config <path>] [--json]

All generation logic lives in cypera-core (pure); this crate owns argv, cypera.toml discovery, filesystem walks, process spawning, and stdout.

Modules: check. Entry: src/lib.rs.
